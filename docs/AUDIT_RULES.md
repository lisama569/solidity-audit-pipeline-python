# 审计规则说明

本流水线内置两条规则族，规则 ID 在所有版本中保持稳定，可作为外部系统
引用、屏蔽（suppress）或对账的依据。规则实现为**纯函数**：只依赖归一化后的
合约项目，不读取时钟、随机数或任何外部环境，因此同一份输入永远得到同一份输出。

## 规则一览

| 规则 ID | 类别 | 触发对象 | 严重程度 |
|---|---|---|---|
| `REENTRANCY-001` | reentrancy（重入） | 状态更新之前发生的外部调用 | HIGH（同函数）/ CRITICAL（跨函数） |
| `DANGEROUS-CALL-001` | dangerous-external-call（危险外部调用） | 未检查返回值的低级 `call`、任意 `delegatecall` | MEDIUM / HIGH |

规则按固定注册顺序执行（`REENTRANCY-001` 在前），报告中的 `rules_evaluated`
字段按此顺序列出全部被评估的规则，即使没有任何命中也会明确给出。

## REENTRANCY-001 重入

### 判定模型

分析器对每个非 `interface`/`library`、且函数体存在的合约做如下分析：

1. **外部调用识别**（同时覆盖低级与高级调用）：
   - 低级：`<expr>.call{...}("")`、`.delegatecall`、`.staticcall`、`.send`、`.transfer`；
   - 高级：`<对象>.<方法>(...)`，其中对象不是函数局部变量也不是语言内建。
   - `transfer`/`send` 只转发 2300 gas，默认不构成重入面，因此不参与重入判定。
2. **状态访问顺序**：把函数体展开为线性语句序列，记录每条语句对合约状态变量的
   读/写集合（支持映射槽 `balances[k] -= v`、元组左值 `(a, b) = ...`、`delete`）。
3. 仅当函数可被外部触达（`external`/`public`）且**调用点之后**才写入状态变量时
   才可能命中。

### 两个变体的区分

- **跨函数重入（CRITICAL）**：调用后写入的状态变量，同时可被本合约中另一个
  未加锁的 `public`/`external` 兄弟函数写入。攻击者即使不能直接重入当前函数，
  也可在外部调用返回前重入这些兄弟函数非法获利。
  - 证据字段 `unguarded_sibling_writers` 明确列出被识别为利用路径的兄弟函数名。
- **同函数重入（HIGH）**：不存在上述未加锁兄弟写入口，但当前函数自身在调用后
  才更新其此前读取/依赖的状态（典型的 DAO 模式）。

### 互斥锁识别（受锁保护重入的对照）

函数若应用了一个被结构判定为**互斥锁守卫**的 modifier，则不报重入。
互斥锁的判据完全基于结构，而非名字（即使把 `nonReentrant` 改名为 `myLock`
也能识别；反之只有名字没有结构不会被当成锁）：

1. modifier 体内存在 `_;` 占位符；
2. 在占位符之前存在形如 `require(<状态变量> ...)` 的守卫，且对该合约的
   某个**状态变量**取反或与 `false` 比较，例如：
   - `require(!locked);`
   - `require(entered == false);`

典型的布尔锁、OpenZeppelin v4 数字锁的“进入前 require 未占用”结构都可被识别。

## DANGEROUS-CALL-001 危险外部调用

- **`delegatecall`（HIGH）**：外部代码在本合约的存储与地址上下文中执行，
  目标不可信时可完全接管合约状态，因此无条件报告。
- **未检查返回值的低级 `call`（MEDIUM）**：以下任一情况视为“已检查”，不报告：
  - 调用直接位于 `require(...)` 之内；
  - 返回值被绑定到具名变量（如 `(bool ok, ) = target.call(...)`），且该变量
    在后续语句的 `require(...)` 或 `if`/`while` 条件中被使用。
- `transfer`/`send` 的 gas 与语义受限，不在本规则中重复报告。

## 多规则命中的合并

同一条问题（按文件 + 合约 + 函数 + 行 + 列定位）被多条规则命中时**合并为一条
结论**：

- `rule_ids` 收集全部命中规则（稳定的字母序列）；
- 严重程度取其中最高者；
- `evidence` 为全部证据去重后的有序并集；
- 主标题/分类取严重程度最高的规则。

例如“未检查返回值且先外呼后更新状态”的调用点会同时命中两条规则，但报告中
只出现一条结论，其 `rule_ids` 为
`["DANGEROUS-CALL-001", "REENTRANCY-001"]`。

## 稳定编号与排序

合并后的结论按以下键确定性排序，再依次编号为 `F-0001`、`F-0002`……：

1. 严重程度降序（CRITICAL > HIGH > MEDIUM > LOW > INFO）；
2. 文件路径、行号、列号升序；
3. 类别、标题、去重键升序。

因此同一输入无论重复多少次、以何种顺序/并发提交，编号与排列完全一致。

## 明确的“无结论”结论

当没有任何规则命中时，报告不会是空的或被静默丢弃，而是显式给出：

```json
{
  "no_findings": true,
  "conclusion": "未命中任何审计规则：在已评估的规则集合下未发现已知风险模式。",
  "rules_evaluated": ["REENTRANCY-001", "DANGEROUS-CALL-001"]
}
```

这表示“在当前规则集覆盖范围内未发现问题”，而非对合约安全性的绝对背书。

## 能力边界（诚实地说明）

- 解析器为审计目的自建的最小 Solidity 语法前端，覆盖合约、状态变量、
  函数、modifier、import 与语句级 token 结构，但不是完整 ABI 编译器；
- 跨文件继承的状态/modifier 不做跨合约合并分析（每个合约独立分析）；
- 重入分析对“外部对象”的识别基于“非局部变量的点链调用”这一句法近似，
  极端动态分派场景可能保守漏报。
